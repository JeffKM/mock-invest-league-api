# mock-invest-league-api

여러 모의투자 대회를 동시에 운영하는 Spring Boot API 서버입니다. 참가자는 대회마다 같은 가상 자금으로 가상 상장사 24곳의 주식을 사고팔고, 총자산으로 순위를 겨룹니다.

> 가상 상장사·공시는 모두 지어낸 것이며 실존 기업과 관계없습니다.

**돈이 걸린 서버에서 생기는 문제를 테스트로 먼저 재현하고, 해결책은 측정해서 고른 기록입니다.** 각 결정의 근거와 실험 과정은 [ROADMAP.md](ROADMAP.md)에 단계별로 남겼습니다.

## 측정한 것

| 주제 | 무엇을 했나 | 결과 |
|---|---|---|
| 동시 주문 | 같은 계좌로 1주 매수 100건을 32스레드로 동시에 보냄 | 락이 없으면 **현금 7,597,800원이 생겨남**. 락 3종을 같은 시나리오 4개로 비교 |
| 락 선택 | 비관적 락 / 낙관적 락 / 조건부 UPDATE | 낙관적 락(재시도 5회)은 매수 100건 중 **57건 실패**. 기본값은 비관적 락 |
| 조회 성능 | `EXPLAIN (ANALYZE, BUFFERS)`로 느린 쿼리 찾기 | 현재가 **166 ms → 1.1 ms**, 내 주문 목록 **34 ms → 0.4 ms** |
| 캐시 | 캐시 없음 / 서버 메모리(Caffeine) / Redis를 같은 부하로 비교 | 요청당 DB 블록 **5~9배 감소**. 서버 한 대라 Caffeine 선택 |
| 부하 테스트 | k6로 주문·조회 혼합 부하, JFR로 원인 추적 | 과부하 때 오류 로그가 클래스 로더 잠금을 잡아 악순환. 잠금 대기 **1,086초 → 5초**, 실패 응답은 전부 503 |
| 테스트 | Testcontainers PostgreSQL로 실제 DB에서 실행 | **155개 통과**, 라인 커버리지 **92.5%**, 브랜치 79.9% |

위 표의 수치는 노트북 한 대(4코어 1.4GHz)에서 잰 값입니다. 시간은 기계 부하에 따라 흔들리므로, 흔들리지 않는 지표(DB 블록 수, 잠금 대기 시간, 오류 수)를 함께 봤습니다. 배포한 뒤 운영 서버(EC2 + RDS)에서 잰 것은 [아래 절](#운영-서버에서-재고-고친-것)에 따로 모았습니다.

## 해결한 문제

### 1. 동시 주문과 잔고 정합성

- **문제.** 같은 계좌로 주문이 동시에 오면 두 요청이 같은 잔고를 읽고 각자 뺀 값을 써서, 한쪽 차감이 사라집니다(갱신 손실). `CHECK (cash >= 0)`으로는 막지 못합니다. 쓰인 값 자체는 양수이기 때문입니다.
- **한 일.** `CountDownLatch`로 출발선을 맞춰 갱신 손실을 재현하는 테스트를 먼저 만들고, 같은 테스트로 비관적 락·낙관적 락·조건부 UPDATE를 비교했습니다. 4개 방식(락 없음 포함) × 4개 시나리오 = 16개 테스트가 CI에서 계속 돕니다.
- **고른 것.** 비관적 락(`SELECT … FOR UPDATE`). 충돌 대상이 "한 사람의 계좌"라 기다리는 비용이 작고, 돈은 실패보다 기다림이 낫습니다. 조건부 UPDATE가 가장 빨랐지만 매도 원가 계산 규칙이 SQL에도 생겨 규칙이 두 곳으로 갈라집니다. 방식은 설정(`league.order.lock-strategy`)으로 바꿀 수 있습니다.
- **증명.** 모든 방식·시나리오에서 `현금 + 묶인 현금 = 원장 합계`(불변식 I5)를 확인합니다.

### 2. 재전송된 주문은 한 번만

`Idempotency-Key` 헤더로 같은 주문을 한 번만 실행합니다. 키를 확인하기 **전에** 계좌 행을 잠그기 때문에, 같은 키로 10건이 동시에 와도 재시도 없이 주문 1건만 생기고 10건 모두 같은 응답을 받습니다. 같은 키로 다른 내용을 보내면 422입니다.

### 3. 가격과 배치: 같은 입력 → 같은 결과

- 가격은 기하 브라운 운동으로 만들고, **같은 시드면 같은 경로**가 나옵니다. 하루치 가격(종목 24 × 78틱)을 배치가 미리 만들어 두고, 조회는 "지금 시각까지의 틱"만 봅니다(미래 가격 차단, I11).
- 지정가 주문은 현금·수량을 묶어 두고, 미리 만든 경로에서 **처음 가격이 닿은 틱**으로 소급 정산합니다. 체결·취소·만료 중 정확히 하나로 끝나며, 배치를 두 번 돌려도 결과가 같습니다(I10).
- 가상 공시는 가격과 함께 결정적으로 만들고, 공시 충격 크기는 몬테카를로로 정했습니다. 출석 보너스의 하루 1회는 DB 기본키에 맡겼습니다.

### 4. 조회 성능: EXPLAIN으로 찾고, 고치고, 다시 재기

| 쿼리 | 원인 | 고친 것 | 시간 | 읽은 블록 |
|---|---|---|---|---|
| 현재가(종목 24개 최신 가격) | `distinct on`이 대회 전체 가격을 읽음 | `LATERAL` + `limit 1` | 166 → 1.1 ms | 3,055 → 98 |
| 순위 스냅샷 총자산 | 같은 원인 | 위 문장 재사용 | 197 → 43 ms | 3,522 → 565 |
| 내 주문 목록(최근 50건) | 플래너가 기본키를 뒤에서 훑음 | 정렬과 인덱스 순서를 같게 | 34 → 0.4 ms | 2,276 → 16 |
| 가격 하루치 INSERT(1,872행) | 문장 1,872개 | `reWriteBatchedInserts` | 744 → 484 ms | — |

모든 실험은 "고치기 전과 결과가 같은지"를 먼저 확인한 뒤 시간을 쟀습니다. 처음 측정 데이터가 "최선의 경우"여서 문제가 안 보였던 것을 발견하고, 데이터를 바꿔 다시 쟀습니다.

### 5. 캐시: 만료 대신 버전 키

시세와 순위는 5분 틱마다만 바뀝니다. 그래서 TTL로 지우는 대신 **틱 번호를 캐시 키에 넣었습니다.** 틱이 바뀌면 새 키가 되므로 낡은 값을 돌려줄 수 없습니다. 같은 키의 값은 바뀌지 않으므로 서버가 여러 대여도 서버마다 따로 캐시해도 됩니다. 그래서 Redis 대신 서버 메모리(Caffeine)를 기본으로 했습니다. Redis 구현도 설정 하나로 켤 수 있습니다.

### 6. 과부하에서 무너지는 고리 끊기

k6로 가정 트래픽(초당 주문 30, 조회 90)을 보내자 실패 64%, p95 55초로 무너졌습니다. JFR로 보니 커넥션 부족 → 예외 스택 트레이스 로그 → 로그가 스택 줄마다 jar 정보를 찾느라 클래스 로더 잠금 → 요청이 더 느려져 커넥션을 더 오래 잡는 악순환이었습니다.

- 커넥션을 못 얻으면 **503 + `Retry-After`**와 한 줄 경고 로그로 응답
- 예외 로그에서 jar 정보 계산을 끔(`logging.exception-conversion-word: "%ex"`)

잠금 대기는 1,086초에서 5초로 줄었고, 같은 부하에서 실패 응답은 전부 503(500은 0건)이 됐습니다. 앱 CPU 2개로는 초당 약 60건까지 p95 63 ms로 여유가 있었고, CPU 4개에서는 초당 120건을 실패 없이 받았습니다. 병목은 앱 CPU입니다.

측정 중 "GC를 바꾸니 빨라졌다"는 결론이 나왔다가, 원래 설정으로 다시 돌려 보니 더 빨랐습니다. 측정 기계가 한가해진 것이었습니다. 그 뒤로 설정을 바꾸면 A → B → A로 확인하고, 실행마다 기계 부하를 결과에 함께 적습니다.

## 운영 서버에서 재고 고친 것

EC2(t3.micro, 메모리 1GB) + RDS(db.t4g.micro)에 올린 뒤, 실제로 일어날 상황을 시나리오 15개(평소 4 · 문제 유발 11)로 만들어 k6로 재현했습니다. 시나리오마다 **측정 → 원인 분석 → 해결 → 같은 조건으로 재측정**을 했고, 서버 쪽은 Prometheus·Grafana와 DB 세션·커널 카운터를 1초 단위로 같이 기록했습니다. 자세한 그래프와 읽는 법은 [측정 보고서](docs/07-측정-보고서.md)에 있습니다.

| 시나리오 | 처음 본 것 | 원인 | 한 일 | 다시 잰 결과 |
|---|---|---|---|---|
| 한 계좌에 주문 몰림(초당 100건) | 커넥션 10/10, 대기 22, p99 최대 757 ms | 한 계좌 잠금 앞의 줄 + 매분 하이퍼바이저 CPU steal | 사용자별 주문 속도 제한(커넥션을 잡기 전에 429) | 커넥션 대기 **0**, 받아들인 주문 p99 **126 ms** |
| 재시작 뒤 첫 몰림(콜드 스타트) | 커넥션 대기 53, p95 282 ms | JIT 컴파일이 코어 2개 중 1.9개를 씀 | 준비 완료 전에 자기 자신에게 조회 20초(데우기), 헬스 체크와 연결 | 대기 **0**, p95 **18 ms** |
| 틱 경계 캐시 스탬피드 | 틱마다 같은 키를 1~2명이 따로 DB에서 읽음 | 버전 키가 틱마다 한꺼번에 바뀜 | single-flight(같은 키는 한 명만 읽고 나머지는 기다림) | 틱마다 DB 읽기 **1번** |
| 정산 폭주 · 취소 경쟁(지정가 1만 건) | 정산 52초, 다음 분 정산과 겹침 | 예약 작업이 스레드 하나를 같이 씀 | 스케줄러 스레드 3개 | 두 번 체결 **0**, 불변식 위반 **0**. 한계는 1분에 약 1만 건 |
| 재전송 폭주(평소의 12배) | 서버는 초당 1,330건을 처리했는데 2초 안에 받은 건 **45%** | 넘치는 요청을 거절하지 않고 줄 세움 | 덜어내기: 동시 20건 넘으면 바로 503 + `Retry-After` | 정점에서 2초 안 성공 **1.9배**, 회복 구간 실패 **0%** |
| 가입 몰림 | 17~27초 동안 모든 요청이 멈춤 | (가설이던 참가 경합이 아니라) 힙 75%가 1GB 서버에서 스왑으로 밀려 Full GC | 힙 40%, 톰캣 스레드 200 → 50 | 가장 긴 GC **7.5 → 0.31초**, 운영 설정에서 스왑 0 |
| 장 시작 몰림(1초 만에 12배) | 연결 맺기 최대 29.7초, 네트워크 오류 345 | 커널의 연결 추적 표(7,680칸)가 가득 참 | 표 65,536칸 · TIME_WAIT 30초, 접속 대기열 1,024 | 연결 최대 **0.76초**, 네트워크 오류 **0** |
| 트래픽 중 배포 | 19.8초 끊김 | 새 JVM 기동 17.5초 | 클래스 공유(AppCDS) | 끊김 **13.1초**, 힙 밖 메모리 188 → 99MB. 남은 끊김은 "장 마감 뒤 배포"로 |
| DB 재부팅 | 앱에서 본 장애 7~14초, 500 10건 | 롤백 실패가 원래 오류(DB 종료)를 덮어 처리기 마지막 칸으로 떨어짐 | 실제 예외 사슬로 테스트를 만들고 503으로 분류 | 자동 회복, 500 **0** |
| 참가자 10만 명 순위 스냅샷 | 5.75초, 플래너가 종목 24개를 1개로 예상 | 새 대회 번호에 통계가 없음 | 대회 시작 때 `ANALYZE` | 예상이 실제와 맞음. 시간은 흔들림 안이라 단축으로 세지 않음(3~4초는 순위 10만 줄 쓰기) |
| CPU 크레딧 소진 | 평소 부하에서도 실패 14.3%, 몰림 뒤 48.8%로 회복 못 함 | 평소 부하(CPU 11~14%)가 이미 기준선 10% 위 | 코드가 아닌 운영 대응: 크레딧 잔액 경보 | 평소 부하라면 바닥까지 약 120시간, 경보로 미리 안다 |
| 30분 장시간 부하 | 누수 없음(힙·파일·커넥션 일정), 가끔 15~26초 DB 멈춤 | **원인 미정**(앱 CPU·GC, RDS CPU·디스크·백업은 지움) | 다음에 잡을 1초 단위 기록 장치(`stall-watch.sh`) | — |

모든 시나리오에서 장부 불변식(현금 + 묶인 현금 = 원장 합계 등) 위반은 0건이었습니다.

**틀렸던 것도 남겼습니다.**

- 가입 몰림은 "같은 대회에 참가하려는 잠금 경합"이라고 짐작했지만, 동시 참가를 따로 재 보니 경합은 없었습니다. 원인은 메모리 설정이었습니다.
- 장 시작 몰림을 재다가 커널 로그에서 연결 추적 표가 찬 기록을 찾았습니다. 시각을 맞춰 보니 그전의 12배 측정에도 섞여 있어서, 보고서의 앞선 결론에 단서를 달았습니다.
- 순위 스냅샷의 "ANALYZE로 절반"은 한 쌍만 비교한 값이었습니다. 다섯 번씩 다시 재니 차이가 흔들림 안이라 결론을 고쳤습니다.
- DB 재부팅의 첫 수정은 원래 오류가 원인 사슬에 남는다고 짐작해 만들었고, 다시 재니 500이 그대로였습니다. 서버 로그의 실제 스택으로 테스트를 다시 만들어 고쳤습니다.

## 구조

```
클라이언트 ──HTTP──▶ Spring MVC
                     ├─ order    주문(시장가·지정가·취소), 멱등성, 락 전략
                     ├─ account  참가, 내 계좌, 출석
                     ├─ market   가격 엔진, 공시, 현재가(캐시)
                     ├─ ranking  순위 스냅샷, 순위표(캐시)
                     ├─ contest  대회 생성·시작, 일일 배치(스케줄러), 관리자 API
                     └─ common   오류 응답(ApiResponse), 시계, 관리자 토큰
                            │
                            ▼
                     PostgreSQL 16 (Flyway 마이그레이션 4개)
```

- 모든 응답은 `ApiResponse<T>` 형식이고, 오류는 `ErrorCode` 하나에서 상태 코드와 메시지를 정합니다.
- 시각은 주입한 `Clock`에서만 읽습니다. 테스트와 부하 테스트는 시계를 고정해 밤에도 장 시간처럼 돕니다.
- 금액은 모두 원 단위 `long`이고, 수수료 계산 함수는 한 곳에만 있습니다.

| GET | `/api/contests/{id}/disclosures` | 공시(지금까지 나온 것만) |
| POST | `/api/admin/contests` | 대회 만들기(관리자) |
| POST | `/api/admin/contests/{id}/start` | 대회 시작(관리자) |
| POST | `/api/admin/contests/{id}/ranking-snapshots` | 순위 스냅샷 바로 찍기(관리자) |

관리자 API는 `X-Admin-Token` 헤더가 필요합니다. 앱을 띄우면 `/swagger-ui.html`에서 모두 볼 수 있습니다.

## 실행

```bash
docker compose up -d          # 로컬 PostgreSQL(5433)
./gradlew bootRun             # http://localhost:8080/swagger-ui.html
./run_tests.sh                # 전체 테스트(도커 필요, 워치독 포함)
./scripts/load-test.sh 1 2m   # k6 부하 테스트(앱 이미지·k6 필요). 결과는 build/k6/
./scripts/load-test-remote.sh http://<서버> 1 2m   # 배포한 서버에 k6(ADMIN_TOKEN 환경 변수, 평일 장 시간)
```

## 배포

- **CI(GitHub Actions):** 올릴 때마다 테스트와 이미지 빌드를 합니다. main에 올라온 커밋은 커밋 sha 태그로 ghcr.io에 이미지를 올립니다.
- **운영 설정(`prod`):** DB 주소·비밀번호·관리자 토큰은 환경 변수로만 받고, 하나라도 빠지면 앱이 뜨지 않습니다.
- **배포 스크립트(`deploy/deploy.sh`):** 새 이미지를 띄운 뒤 헬스 체크를 기다리고, 실패하면 직전 이미지로 자동으로 되돌립니다.
- **대상:** AWS 시드니 리전의 EC2(t3.micro, Docker) + RDS PostgreSQL 16(db.t4g.micro, 인터넷에서 접근 불가). 2026-11-13 첫 배포. 순서, 비용, 첫 배포에서 막혔던 곳은 [docs/05](docs/05-배포-AWS.md)에 있습니다.

## 아직 하지 않은 것

- **무중단 배포:** 새 JVM이 뜨는 동안 옛 JVM이 요청을 받으려면 두 벌이 동시에 떠야 하는데, 1GB 서버 한 대에는 메모리가 모자랍니다. 서버 두 대 + 로드 밸런서가 필요합니다.
- **30분 부하 중 가끔 생기는 DB 멈춤의 원인**
- **HTTPS·자동 배포(CD)**
- **서버 두 대 이상일 때의 스케줄러 중복 실행 방지(ShedLock 등)**
