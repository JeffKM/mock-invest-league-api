# 06. 부하 시나리오와 관측

부하 테스트의 목적은 숫자 하나를 얻는 것이 아니라 **문제를 드러내고, 그래프로 원인을 찾고, 고친 뒤 다시 재서 확인하는 것**이다.
이 문서는 (1) 무엇을 흉내 낼지(시나리오 목록), (2) 결과를 어디서 어떻게 볼지(관측), (3) 문제 하나를 끝까지 다루는 순서를 정한다.

원칙: **문제를 만들려고 버그를 심지 않는다.** 시나리오는 지금 코드가 실제로 약할 수 있는 곳을 겨냥한다.
문제가 안 나오면 "버텼다"가 결과이고, 그 근거(그래프)를 남긴다.

## 1. 시나리오 목록

### 정상(기준선)

| # | 이름 | 내용 | 확인할 것 | 상태 |
|---|---|---|---|---|
| N1 | `steady` | 평소 속도(가정 트래픽의 1배: 주문 30 + 조회 90 TPS)를 일정하게 2분 | 모든 비교의 기준값 | 있음 |
| N2 | `journey` | 계좌 → 공시 → 매수 → 주문 확인 → 지정가 걸고 취소 또는 매도 → 순위. 사이사이 생각하는 시간 | 매도·취소가 섞여도 지연이 안정적인지 | 있음 |
| N3 | `soak` | 1배로 30~60분 | 메모리·커넥션이 새는지, GC 가 점점 길어지는지 | 예정 |
| N4 | `capacity` | 실패할 때까지 조금씩 올림 | 이 서버의 최대 처리량 | 예정 |

### 문제 유발(코드에서 찾은 약점 후보)

| # | 이름 | 실제 상황 | 의심하는 원인(가설) | 상태 |
|---|---|---|---|---|
| P1 | `hot` | 버튼 연타·재전송, 계좌 몇 개로 몰림 | 계좌 행 잠금(`FOR UPDATE`)을 기다리는 동안 커넥션을 쥐고 있어 풀(10개)이 바닥남 → 503 | 있음 |
| P2 | `rush` | 09:00 장 시작 몰림(4배로 30초) | 대기열이 쌓이고, 몰림이 끝난 뒤 회복이 늦음 | 있음 |
| P3 | `tick` | 5분마다 새 가격이 뜨면 다들 계좌·순위를 엶 | 틱이 바뀌면 캐시 키가 바뀌어 모두 동시에 캐시를 놓침(캐시 스탬피드) | 있음 |
| P4 | `settle-storm` | 대기 지정가 수천 건 + 매분 정산 배치 + 사용자 주문 | 배치가 한 건씩 처리해 1분 안에 못 끝남, 같은 계좌를 두고 사용자 주문과 잠금 경합 | 예정 |
| P5 | `cancel-race` | 배치가 체결하는 순간 사용자가 취소 | 둘이 겹치면 돈·수량이 두 번 계산될 수 있음 → 불변식 검사로 확인 | 예정 |
| P6 | `snapshot-load` | 참가자 수만 명일 때 순위 스냅샷 + 순위 조회 | 스냅샷 쿼리가 무거움, 새 스냅샷 직후 캐시 스탬피드 | 예정 |
| P7 | `join-storm` | 대회 공지 직후 1분에 수천 명 가입·참가 | 초기 현금 원장 쓰기, 고유 제약 충돌 | 예정 |
| P8 | `retry-storm` | 클라이언트가 2초 만에 포기하고 같은 키로 재전송 | 처리 중인데 같은 키가 또 옴 → 중복 주문 또는 409 남발 | 예정 |
| P9 | `db-failover` | 측정 중 RDS 재부팅(장애 주입) | 몇 초 만에 회복하는지, 500 이 몇 건인지 | 예정 |
| P10 | `deploy-under-load` | 트래픽 중 `deploy.sh` | 인스턴스 하나라 몇 초 끊김 → 무중단 배포 | 예정 |
| P11 | `credit-drain` | 긴 고부하로 t3 CPU 크레딧 소진 | CPU 가 기본 성능으로 묶여 지연 급증. 코드 한계와 기계 한계 구분 | 예정 |

모든 시나리오 공통 통과 기준: 500 류 0건(`server_errors_not_503`), 끝난 뒤 불변식 위반 0건(`invariant_violations`).

## 2. 관측: 세 군데에서 본다

| 무엇 | 어디서 | 보여주는 것 |
|---|---|---|
| k6 HTML 리포트 | 측정 결과 폴더의 `report.html` (브라우저로 열기) | 사용자 쪽: 보낸 요청 수, 응답 시간, 실패를 시간 순으로 |
| Grafana | 노트북 `http://localhost:3000` 대시보드 "모의투자 서버" | 서버 안: API 별 지연(p95·p99), 응답 상태(409·503·500), DB 커넥션 풀(사용 중·대기·얻는 시간·쥐고 있던 시간), CPU, 톰캣 스레드, 힙·GC, 주문 재시도, 캐시 적중 |
| CloudWatch | AWS 콘솔 | 기계: EC2 CPU·CPU 크레딧, RDS CPU·연결 수 |

### 띄우는 법

```bash
# 로컬에서 잴 때
monitoring/up.sh local                          # Prometheus + Grafana (노트북 Docker, AWS 비용 없음)
SCENARIO=hot scripts/load-test.sh 1 2m          # 끝에 report.html 경로와 Grafana 시간 범위 링크가 나온다

# 배포한 서버를 잴 때 (서버 .env: ACTUATOR_EXPOSE=health,info,metrics,prometheus)
monitoring/up.sh 3.107.29.43                    # 노트북 Grafana 가 서버 지표를 5초마다 가져온다
SCENARIO=hot scripts/load-test-remote.sh http://3.107.29.43 1 2m cloudshell   # CloudShell 에서

monitoring/down.sh                              # 끄기(수집한 데이터는 30일 남는다)
```

### 그래프 읽는 순서(점검표, 대시보드 맨 위에도 있다)

1. **사용자가 느리다고 느꼈나?** p95 응답 시간이 올라간 구간을 찾고, 그 시각을 기준으로 아래를 본다.
2. **DB 커넥션을 기다렸나?** 대기(pending) > 0, 커넥션 얻는 시간이 길다 → 풀이 모자라거나 **누가 커넥션을 오래 쥐고 있다**(쥐고 있던 시간).
3. **기계가 꽉 찼나?** CPU 가 100% 에 붙었으면 코드보다 기계 한계(EC2 는 CPU 크레딧도).
4. **요청을 버렸나?** 503(덜어냄)·5xx(오류)가 언제 시작했는지, 몰림과 같은 시각인지. 409 는 업무상 거절이라 정상.

## 3. 문제 하나를 끝까지 다루는 순서

ROADMAP 에 사례마다 이 순서로 남기고, 포트폴리오의 "문제 해결 사례"는 여기서 고른다.

1. **현상**: 어떤 시나리오에서 무엇이 얼마나 나빴나(k6 표 + 리포트 캡처)
2. **분석**: 같은 시각의 Grafana 에서 무엇을 봤고, 그래서 원인을 무엇으로 판단했나(캡처). 다른 후보를 어떻게 지웠나
3. **해결**: 고른 방법과 고르지 않은 방법, 그 이유
4. **재측정**: 같은 시나리오·같은 조건으로 다시. 전후 그래프를 나란히
5. **불변식**: 고친 뒤에도 위반 0건인지

측정마다 그래프를 어떻게 읽었는지는 [docs/07 측정 보고서](07-측정-보고서.md)에 시나리오별로 남긴다.
