# 08. 결정 기록: 본 API 는 Tomcat, 시세 푸시만 Netty

- 상태: 채택(2026-11-21)
- 근거: ROADMAP 42단계(본 API), 43단계(시세 푸시 실험)

## 질문

"요청마다 스레드를 하나씩 쓰는 톰캣(Spring MVC) 대신, 적은 스레드로 많은 연결을 다루는 Netty(Spring WebFlux)를 쓰면 더 많이 받지 않나?"

답은 일의 종류마다 다르다. **짧게 묻고 답하는 본 API** 와 **연결을 오래 쥐는 시세 푸시** 를 따로 판단했다.

## 1. 본 API: Tomcat 그대로

### 판단에 쓴 측정(운영과 같은 EC2 t3.micro + RDS db.t4g.micro)

| 측정 | 숫자 | 출처 |
|---|---|---|
| 최대 처리량에서 무엇이 먼저 찼나 | 초당 1,330~1,410건에서 **앱 CPU 91%, DB 커넥션 대기 190**. 그때 톰캣 스레드 200개도 다 찼지만, 스레드들은 커넥션을 기다리며 줄 서 있었다 | ROADMAP 30단계 |
| 스레드가 적어도 처리량이 나오나 | 덜어내기(동시 20) 운영 설정, 12배 몰림: **스레드 23개로 2xx 초당 1,080건** | ROADMAP 32단계 |
| 스레드가 많으면 무엇이 나빠졌나 | 스레드 200개 몫의 메모리까지 더해 앱이 760MB 로 커졌고, 스왑된 힙을 GC 가 훑느라 17~27초 멈췄다. 스레드 50개 + 힙 40% 로 줄여 스왑 0 | ROADMAP 31단계 |
| 수십 초 연결 지연은 어디서 | 앱이 아니라 커널의 연결 추적 표(서버·컨테이너 두 겹)가 SYN 을 버린 것 | ROADMAP 32·41단계 |
| 요청 하나가 하는 일 | 거의 모든 요청이 JDBC(JPA)로 DB 를 부른다. 커넥션 10개. 바깥 API 호출은 요청 경로에 없다 | 코드, ROADMAP 39단계 |

### 판단

1. **병목은 스레드가 아니다.** 한계에서 먼저 찬 것은 CPU 와 DB 커넥션 10개다. 이벤트 루프는 CPU 를 늘려 주지 않고, DB 커넥션 수도 그대로다.
2. **줄의 자리만 바뀐다.** 넘치는 요청은 줄 세우지 않고 바로 거절한다(30·32단계). WebFlux 로 동시 연결을 더 받아도 그 요청들은 DB 커넥션 10개 앞에서 다시 줄을 선다.
3. **끝까지 논블로킹이 아니면 이득이 없다.** WebFlux 에서 JDBC·JPA 를 부르면 별도 스레드 풀(`boundedElastic`)로 넘겨야 한다. 제대로 하려면 R2DBC 로 낙관적 락·트랜잭션 코드를 다시 써야 한다.
4. **스레드가 문제였던 한 번은 수를 줄여서 풀었다(31단계).**

## 2. 시세 푸시: Netty

가격·순위는 틱(5분)마다 바뀌는데 클라이언트는 계속 조회한다. 바뀔 때만 밀어 주는 SSE 가 맞다. SSE 는 연결을 오래 쥔다. Tomcat(MVC `SseEmitter`)으로 먼저 만들어 무엇이 깨지는지 재현했다(노트북, 클라이언트는 다른 프로세스).

| | MVC + Tomcat | WebFlux + Tomcat | WebFlux + Netty |
|---|---|---|---|
| 느린 연결 5개가 끼면(정상 200) | **방송 300초 멈춤**(5 × 쓰기 시간 제한 60초) | 안 멈춤 | 안 멈춤 |
| 3,000 연결: 연결당 힙 | 100~106 KB | 112~118 KB | **12.6~13.2 KB** |
| 3,000 연결: 늘어난 RSS | +354 MB | — | **+140 MB** |
| 서버 스레드 | 50 | 200 | 8 |

### 판단

1. **느린 클라이언트 문제는 모델의 문제다.** MVC `SseEmitter.send` 는 소켓에 블로킹으로 써서, 느린 연결 하나가 방송 반복문 전체를 막는다. WebFlux 는 연결마다 논블로킹으로 쓰고, 못 받아 가는 연결은 그 연결의 버퍼(최근 16개)만 차고 오래된 것부터 버린다. Tomcat 위의 WebFlux 도 이건 풀었다.
2. **Netty 를 고른 이유는 메모리다.** 같은 WebFlux 코드에서 서버만 바꾸면 연결당 힙이 약 9분의 1, 프로세스 전체로 약 2.5분의 1이다. 운영 힙 280MB 로 Tomcat SSE 는 약 2,500 연결이 한계, Netty 는 1만 5천 이상이다.
3. **그래서 푸시만 따로 띄운다(`league-push`).** 본 API 는 1번 판단대로 Tomcat 에 두고, 연결을 오래 쥐는 일만 Netty 서버가 맡는다. 둘은 Redis pub/sub 으로 잇는다.

## 대가(받아들인 것)

- 서버가 둘이 된다(배포·모니터링 대상이 늘고, 1GB 서버에 JVM 이 둘).
- 느린 연결은 중간 시세를 놓칠 수 있다(최근 16개만 둠). 시세는 최신 값만 의미가 있어서 받아들인다.
- 순간 몰림에서 본 API 는 503 으로 거절한다(32단계: 4배 몰림 정점 1.98%).

## 다시 판단할 조건

- 본 API 에서 CPU·DB 가 남는데 스레드가 먼저 차는 측정이 나올 때, 또는 요청 경로에 느린 바깥 호출이 들어올 때. 그때도 먼저 볼 것은 가상 스레드(Java 21+, MVC 코드 그대로)다. 지금은 Java 17 이라 해당 없다.
- 푸시 연결 수가 운영 서버 한 대의 메모리를 넘을 때(푸시 서버를 늘린다. Redis pub/sub 이라 서버 수와 상관없이 같은 방송을 받는다).

## 면접에서 한 줄로

"본 API 는 한계에서 먼저 찬 게 CPU 와 DB 커넥션이어서 Tomcat 그대로 두고, 연결을 오래 쥐는 시세 푸시만 Netty 로 뗐습니다. Tomcat SSE 로 먼저 만들어 보니 느린 클라이언트 5명이 방송을 300초 막았는데 이건 WebFlux 의 논블로킹 쓰기로 풀렸고, Netty 를 고른 이유는 연결당 힙이 100KB 에서 13KB 로 줄어서 같은 서버에 6배 많은 연결을 담을 수 있어서입니다."
