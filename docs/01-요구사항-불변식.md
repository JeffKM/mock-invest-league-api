# 01. 요구사항과 불변식

> 상태: 초안(2026-11-10). 본인이 읽고 숫자·규칙을 확정하면 "초안" 표시를 지운다.

## 1. 한 줄 정의

여러 모의투자 대회를 동시에 운영하는 서버. 참가자는 대회마다 같은 가상 자금을 받고, 가상 상장사 주식을 사고팔아 기간 안에 총자산 순위를 겨룬다.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 대회(Contest) | 기간·장 시간·초기 자금·수수료가 정해진 하나의 리그. 여러 개가 동시에 열린다 |
| 상장사(Company) | 가상 회사. 모든 대회가 같은 목록을 쓰지만, 가격 경로는 대회마다 따로 만든다 |
| 참가자(Participant) | 한 사용자가 한 대회에 참가한 계좌. 사용자 1명 = 대회마다 계좌 1개 |
| 틱(Tick) | 가격이 바뀌는 단위 시간. 대회 설정 `tick_seconds`(기본 300초 = 5분) |
| 거래일(Trading day) | 대회 기간 중 장이 열리는 날 |
| 원장(Ledger) | 현금이 움직일 때마다 남기는 한 줄 기록 |

## 3. 기능 요구사항(1차 범위)

### 대회
- F1. 관리자가 대회를 만든다: 이름, 시작일·종료일, 장 시간(기본 09:00~15:30), 초기 자금(기본 10,000,000원), 수수료(기본 0.5%), 가격 제한폭(기본 ±30%), 출석 보너스(기본 50,000원).
- F2. 대회 상태: `SCHEDULED → RUNNING → FINISHED`. 상태는 시각으로 바뀐다(배치).
- F3. 사용자는 `SCHEDULED`·`RUNNING` 대회에 참가할 수 있다. 참가하면 초기 자금이 들어온 계좌가 생긴다.

### 시세
- F4. 장이 닫히면 배치가 다음 거래일의 전체 가격 경로(틱별 가격)를 미리 만든다. 같은 시드 → 항상 같은 경로.
- F5. 현재가 = 지금 시각에 해당하는 틱의 가격. 장 밖이면 마지막 종가.
- F6. 가상 공시: 특정 틱에 회사·섹터 충격을 주는 이벤트. 공시가 공개되는 틱부터 참가자에게 보인다(미래 공시는 숨김).

### 주문
- F7. 시장가 매수·매도: 현재 틱 가격으로 즉시 전량 체결.
- F8. 지정가 매수·매도: 주문 시 자금(매수) 또는 주식(매도)을 묶어 두고, 가격 경로가 지정가에 닿는 첫 틱에 지정가로 전량 체결. 당일 장 마감까지 안 닿으면 만료되고 묶인 것을 돌려준다.
- F9. 대기 중인 지정가 주문은 취소할 수 있다.
- F10. 모든 주문 요청은 `Idempotency-Key` 헤더를 받는다.

### 보너스·순위
- F11. 출석 보너스: 참가자당 하루 1번(한국 시간 기준 날짜).
- F12. 순위: 총자산 = 현금 + 묶인 현금 + Σ(보유 수량 × 현재가). 일정 주기로 스냅샷을 만들고, 조회는 스냅샷 기준.

### 1차 범위에서 뺀 것
부분 체결, 공매도, 신용, 호가창(주문끼리 맞붙이는 매칭 엔진), 실시간 푸시(WebSocket), 소셜 기능. 주문은 서로 맞붙지 않고 미리 만든 가격 경로에 대해서만 체결된다.

## 4. 불변식(항상 참이어야 하는 것)

테스트 이름은 이 번호를 따른다(예: `I1_현금은_음수가_될_수_없다`).

| # | 불변식 | 어디서 지키나 |
|---|---|---|
| I1 | 현금(`cash`)과 묶인 현금(`reserved_cash`)은 0 이상 | 서비스 검증 + DB `CHECK`(마지막 방어선) |
| I2 | 보유 수량과 묶인 수량은 0 이상. 가진 것보다 많이 팔 수 없다(공매도 없음) | 서비스 검증 + DB `CHECK` |
| I3 | 금액은 모두 원 단위 정수(`long`/`bigint`). 소수 금액 없음 | 타입 |
| I4 | 수수료 = 체결 금액 × 수수료율, **원 미만 버림** | 계산 함수 1곳 |
| I5 | 현금 보존: `cash + reserved_cash = Σ 원장 금액`(참가 때 초기 자금을 INITIAL 로 기록하므로 포함) | 통합 테스트로 매번 확인 |
| I6 | 같은 참가자·같은 `Idempotency-Key`의 주문은 한 번만 실행되고, 다시 보내면 처음 결과를 돌려준다 | DB 유니크 제약 + 서비스 |
| I7 | 출석 보너스는 참가자·날짜당 최대 1번 | DB 기본키 `(participant_id, attended_on)` |
| I8 | 틱 가격은 전 거래일 종가 대비 ±가격 제한폭 안 | 가격 엔진 + 테스트 |
| I9 | 주문은 `RUNNING` 대회의 장 시간 안에서만 받는다 | 서비스 검증 |
| I10 | 지정가 주문은 정확히 한 번 끝난다: 체결·취소·만료 중 하나. 정산 배치를 두 번 돌려도 결과가 같다 | 상태 전이 조건부 UPDATE + 테스트 |
| I11 | 미래 틱의 가격과 공시는 API로 볼 수 없다 | 조회 쿼리 조건 |

> DB `CHECK`만으로는 동시성 버그를 못 막는다. 두 요청이 같은 잔고 1,000,000원을 동시에 읽고 각자 600,000원을 빼서 둘 다 400,000원을 쓰면, 값은 음수가 아니지만 돈이 600,000원 생겨난다(갱신 손실). 이것이 2주차 실험의 출발점이다.

## 5. 예상 트래픽 가정

| 항목 | 가정 |
|---|---|
| 동시 진행 대회 | 10개 |
| 대회당 참가자 | 1,000명(전체 10,000명) |
| 장중 피크 주문 | 약 30 TPS(장 시작·마감 직전 몰림) |
| 장중 조회(시세판·내 계좌·순위) | 약 90 TPS |
| 틱당 가격 행 | 대회 10 × 종목 24 = 240행, 하루 78틱 → 하루 약 18,720행 |

5주차 k6로 이 가정의 2~3배까지 확인한다.

## 6. 정할 것(본인)

- [ ] 기본값(초기 자금, 수수료, 제한폭, 보너스, 틱 간격)이 위 숫자로 괜찮은지
- [ ] 인증: 1주차는 `X-User-Id` 헤더로 임시 처리 → 3주차 이후 JWT로 바꿀지
- [ ] 지정가 체결 가격: 지정가로 체결(현재 안) vs 닿은 틱의 가격으로 체결
